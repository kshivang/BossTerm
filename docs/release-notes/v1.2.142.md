# Release Notes - v1.2.142

**Release Date:** 2026-07-28

## Highlights
The collapsed left tab bar now reveals itself on hover instead of demanding a chevron click, sliding the full bar in as an overlay drawer that never resizes the PTY underneath it. And a launch that showed no window for minutes - process alive, logs healthy, JVM near 0% CPU - turns out to have been the bundled fonts being rewritten from scratch on every single launch; they now extract once per upgrade to a content-addressed path.

## New Features
- Resting the pointer on the 44dp icon strip slides the full tab bar in after 150ms and retracts it 250ms after the pointer leaves. The strip appears two ways - a window under 700dp forces it, or the user collapses it with the chevron - and getting the full bar back needed a deliberate click either way, which is a poor fit for a strip you brush past constantly; in the manually-collapsed case there was no drawer at all, just an in-flow rail. The drawer floats over the terminal rather than pushing it, so hovering never triggers a PTY resize. The close delay exceeds the open delay because the drawer slides over the strip, handing hover off between two nodes mid-reveal (#352)
- The revealed drawer's bottom button becomes a pin rather than the collapse chevron - the icon is the state. Pinning persists `tabBarCollapsed = false` so the drawer becomes the real in-flow bar, or in a narrow window where width forces the strip, makes it stay put until dismissed; at that point the chevron returns. Dismissing a reveal suppresses it until the pointer actually leaves, so it can't slide back in under the cursor (#352)
- New `tabBarHoverExpand` setting (Settings > Behavior > Tab Bar), on by default. Turning it off restores the chevron-only behavior exactly (#352)

## Bug Fixes
- A launch could show no window for minutes with the process alive, logs healthy and the JVM near 0% CPU. It looks like a launch blocked by policy; it isn't. Skia's font path needs `dlsym` for the CoreText weight mapping, so it wants dyld's loader read lock, and anything stalling a first-map code-signature check holds the write lock and blocks the first frame - an endpoint-security agent scanning a newly written file being the usual cause. `loadBundledFont` was handing it the perfect input: `File.createTempFile` wrote a fresh 2.5 MB `MesloLGSNF*.ttf` (plus `NotoSansSymbols2`) into the temp dir on every launch, so the scan never got to reuse a verdict. Fonts now extract to `~/.bossterm/fonts/<name>-<sha256-12>.ttf`, written once per font per upgrade, so every later launch opens a file the scanner has already seen. The hash in the name is the invalidation - a new bundled font gets a new path, no version check needed (#353)
- A hover-revealed drawer is a second, short-lived `TabBar` composition, and retraction disposes it - fine for a bar opened with a chevron, not for one that vanishes because you moved the mouse. Right-click was the worst case: `ContextMenuController` pops a native `JPopupMenu` directly under the cursor, so the Compose canvas immediately saw a pointer exit and 250ms later the drawer retracted out from under its own menu. "Rename…" and the remote-group rename became silent no-ops because the composition rendering the text field was gone, and the popup was left orphaned over the terminal. Inline rename lost the edit if the pointer moved aside while typing, and a drag crossing the drawer's edge hit `resetTabDrag()` in the disposal path - the case `TabBar.kt` already warns about. `TabBar` now reports those three interactions as one `onTransientInteraction` flag, a third vote in `hoverRevealTarget` alongside the two hover zones; disposal reports false so no owner is left holding a stale "busy", and also hides the native popup, which nothing else took down (#352)
- `ContextMenuController` gains a `menuVisible` state: `menuState` only ever tracked the Compose fallback, never the native popup that is used in practice (#352)
- Only the chevron-opened drawer keeps its full-screen click-catcher, so a hover-revealed drawer never swallows the click that focuses the terminal (#352)
- Nothing evicted the font cache: the hash in the filename invalidates for lookup but never deletes, so every bundled-font upgrade left the previous multi-megabyte copy behind forever, and a write killed by SIGKILL orphaned its temp - the likely response to a launch showing no window, so not hypothetical. The publish path now drops superseded copies immediately and temps by age, with a one-hour cutoff protecting a concurrent launch's in-flight temp rather than deleting it out from under them. Prune runs on the write path only, so a warm launch still does no I/O beyond the length check (#353)
- The cache name no longer hardcodes `.ttf` - an `.otf` resource was being published as `.ttf` (#353)

## Improvements
- Font publishing goes through a unique temp plus an atomic rename, so two launches racing can't expose a torn file; a short-read copy is republished rather than handed to Skia, and an unusable cache dir falls back to the old per-launch temp so a font always loads (#353)
- Writes now fsync before the rename. A rename is atomic for ordering, not durability: delayed allocation could publish a correctly-sized file with unwritten extents after a power loss, and that file passes the length check forever - unlike truncation, which self-heals. The comment now says what the check does and does not catch (#353)
- The extract is memoized behind a `lazy`, mirroring `bundledSymbolFont`. It was re-paying the 2.5 MB inflate plus SHA-256 on every call, and `loadBundledFont` is reached from `loadTerminalFont`'s fallback under `remember(settings.fontName)` in both `TabbedTerminal` and `EmbeddableTerminal` - so changing the font setting re-hashed on the composition thread (#353)
- AGENTS.md's "Font Loading" note is what pointed at `createTempFile`, so it now documents `extractBundledFont`, plus how to tell this hang apart from an actual launch block: `jcmd` for the EDT's top frame, `sample` for the native leaf, CPU-vs-elapsed to prove blocked rather than spinning. It also warns that inspecting windows with `osascript`/System Events makes macOS `dlopen` the accessibility bundles into the target, piling onto the very same lock and reporting "0 windows" as a false negative (#353)
- The drawer-only wiring folds into a named `SidebarDrawerHooks` instead of a fourth and fifth positional lambda; the reveal debounce is skipped when the target already matches, rather than burning a 250ms coroutine to rewrite false; `revealSuppressed` clears when the setting is toggled off, not just when the strip goes away; the drawer's `hoverable` gate matches the rail's; and `tabBarSummaryMode` is documented alongside the keys added earlier (#352)
- Test coverage for both paths: `SidebarHoverRevealTest` for the reveal target logic, and font-cache cases for reuse (with a back-dated timestamp so a rewrite inside one filesystem-granularity second can't pass), the prune, and the temp fallback when the cache dir is unusable (#352, #353)
