# Release Notes - v1.2.143

**Release Date:** 2026-07-30

## Highlights
The AI menu now leads with the open-source stack: Kimi Code CLI, Grok Build, Hermes Agent, OpenClaw and Ollama join the registry, and ordering is derived from each entry's openness flags rather than stored, so it can't contradict them. On the share viewer, Boss Calling and the mobile on-screen keys collapse into one bottom strip instead of two stacked bars, and the initial paint stops emitting its escape sequences without the ESC byte.

## New Features
- Five new entries in the AI menu: Kimi Code CLI, Grok Build, Hermes Agent, OpenClaw, and Ollama. Menus, detection, onboarding, settings and the remote/share menus all read the registry, so each one arrived as a single `AIAssistants.BUILTIN` entry plus (where it speaks MCP) one `McpAttachTarget` (#354)
- Ollama gets its own `LOCAL_MODEL_RUNTIME` category rather than being filed as another agent — it serves models instead of acting on your behalf, so it has no auto-approve mode and no MCP attach target. New `MenuActions` hooks expose it: `onRunLocalModel`, `onStartLocalModelServer`, `onListLocalModels`. The built-in "Run a Model…" item passes null, which leaves `ollama run ` on the command line unterminated so you type the model yourself — enumerating installed models would mean shelling out while the menu is opening (#354)
- The menu order is now derived from each entry's `openSource` and `localModels` flags — fully-open stacks first, then open clients on vendor models, then proprietary — instead of being stored as declaration order that could silently disagree with the flags (#354)

## Bug Fixes
- `TerminalSnapshotEncoder.encode` built its SGR runs, its trailing reset and its cursor-park sequence with a bare `[` and no ESC byte, so the share viewer's *initial* paint sent literal `[0m` / `[1;1H` text into xterm.js instead of control sequences. The screen-repaint path next to it had the escape right, which is why this survived — live output looked correct and only the first render of retained scrollback was wrong (#355)
- Snapshots carried the cursor's position but not its state, and `viewer.js` resets xterm before applying one — so a host that had hidden its cursor, or set a bar or underline shape, came back as a default steady block on every reconnect and every repaint. `encode` and `encodeScreenRepaint` now append DECTCEM visibility plus the matching DECSCUSR shape, threaded through from `MirrorShare`, `DaemonShareServer` and `DaemonAttachServer` (#355)
- Boss Calling and the on-screen key bar were two separately-positioned fixed elements, each measuring the other to work out its own offset. They now live in one `#bottomstrip` wrapper that owns the fixed positioning, the keyboard offset and the horizontal scroller; `positionBottomStrip` places it once and reserves its measured height, so wrapping can't double-push the terminal, and on a narrow phone the two groups wrap within the same scroller instead of forming a second strip that eats another row of screen (#355)
- The voice toast positioned itself off `voiceBarEl.offsetHeight`, which excludes the strip's keyboard offset, so with the soft keyboard up it could land under the controls it was meant to sit above. It now measures `getBoundingClientRect().top` against the window height (#355)
- Onboarding's Windows install path no longer sniffs the install method out of the command string — each entry declares it, which also makes it testable from any host rather than only from Windows (#354)
- A per-CLI installer that failed no longer aborts the whole onboarding script under `set -e` (#354)
- Grok Build's auto-approve flag is `--always-approve`, not `--yolo`. OpenCode's is an env prefix — its TUI has no flag, and the form its docs show silently approves nothing. Kimi's `mcp.json` schema was read from the binary's own zod definitions. All three were verified against installed binaries rather than documentation (#354)

## Improvements
- Registering a CLI took seven edits, five of them hardcoded duplicates of the registry that failed silently when missed. It now takes one `AIAssistants.BUILTIN` entry plus one `McpAttachTarget`, and `AttachTargetCoverageTest` fails the build if those two registries drift apart (#354)
- Onboarding's assistant detection reuses the batched sweep instead of spawning a login shell per command (#354)
- New `CliConfigPaths` and `McpConfigFileEditor` split config-path resolution and MCP config-file editing out of `McpCliAttacher`, which is what let the per-CLI schema differences (Kimi's included) stop being special cases in the attacher (#354)
- Test coverage for the new surface: `AIAssistantLaunchCommandTest` over the launch lines, `AttachTargetCoverageTest` over registry drift, `McpRegistrationScannerTest`, an expanded `OnboardingInstallScriptTest`, plus `TerminalSnapshotEncoderTest` cases for the cursor-state suffix and a `ShareViewerAssetTest` case for the shared bottom strip (#354, #355)

## Breaking Changes
Published API, embedders only — no behavior change for users of the app:

- `MenuActions`' four per-CLI launch callbacks (`onLaunchClaudeCode`, `onLaunchGemini`, `onLaunchCodex`, `onLaunchOpenCode`) collapse into a single `onLaunchAssistant: ((assistantId: String) -> Unit)?`, which takes an id from `AIAssistantIds`. This is what makes the menu iterable over the registry instead of needing a new callback per CLI. Replace each old assignment with one `onLaunchAssistant` that switches on the id (#354)
- The unused `@Serializable` `AIAssistantConfig` type and `AIAssistants.defaultConfigs()` are removed. Launch lines are built by `ToolCommandProvider.launchCommandText`; nothing read the config type (#354)
