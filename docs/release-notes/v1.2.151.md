# Release Notes - v1.2.151

**Release Date:** 2026-08-21

## Highlights
BossTerm gains two light identities — **BOSS Blueprint Light** and **BOSS Daylight** — mirroring the host's light schemes so the standalone app and the embedded terminal are one product. Getting there meant the frame around the terminal finally follows the active theme: 13 always-visible surfaces that held ~185 colour literals and read no theme token at all now do.

## New Features
- **BOSS Blueprint Light and BOSS Daylight.** Two light themes mirroring BossConsole's `BossBlueprintLightColorScheme` and `BossLightColorScheme`. Each sits next to its dark sibling in both builtin lists, with `boss-blueprint` still leading them; `DEFAULT_THEME_ID` is unchanged
- The surface ladder runs paper → near-white → white rather than copying the host's identical `panel` and `raised`. Here `raised` is the background of every settings row and card and `panel` is the window behind them, and those rows carry no border — white on white erases all of them

## Bug Fixes
- **Chrome ignored the theme entirely.** Picking Solarized Light already gave a light terminal inside a dark window, with `Color.White` text in the tab-rename field and the search bar, on paper. The tab bar, title bar, toasts, split divider and border, scrollbar block markers, search bar, command palette, history overlay, MCP indicator, status strip, update banner and call bar now read tokens
- **Chrome colours could never follow a theme switch.** StatusStrip, HostCallBar, McpStatusIndicator, UpdateUI and TabBar's RemoteAccent held their colours in file-scope `private val`s, initialised once at class-init — so they were frozen even between two dark themes. All are `get() =` now, the rule every member of SettingsTheme already follows
- **The active tab chip had almost no surface on BOSS Blueprint.** TabBar derived it with Compose's `Color` lerp, which interpolates in Oklab, so a small step off a near-black floor (`#05070B`) rounded back to the floor. It reads the `raised` token instead — the same idea computed in gamma sRGB
- **The render guard was rewriting the authored palettes.** `TerminalCanvasRenderer` runs every glyph colour through `ColorUtils.legibleOnLightBackground`, and `convertTerminalColor` resolves indexed 0–15 from the palette *before* that call. Measured, not reasoned about: five of sixteen slots in blueprint-light and two in daylight were mirrored-and-clamped at paint time, so the shipped colour was not the authored one. Worst was the dim slot — ANSI 8 `#7E8797` arrived as `#687181`, one green-channel step from ANSI 7, making the "8 must be dimmer than 7" assertion hold on values no screen ever saw. The affected slots are retuned so the guard is a no-op
- MCP indicator: the dot's 1.dp ring was drawn in the dot's own colour, so the ring that defines a 10.dp dot against the panel was invisible in both states. It is `line2` now, and `McpOffBorderColor` — a pure alias for `alert` at its one remaining site — is gone. Its off label was still `alert`, a fill token at 4.2:1, contradicting a comment that claimed both labels were plain text; both are `chalk`
- HostCallBar's BarButton surface was `panel`, which is also the bar's own background, so a button that used to be recessed had only its border left. It takes `raised`
- SearchBar's match counter took `chalk` while the arrows beside it took `mist`. They were one colour before and are one visual group again

## Improvements
- A light ANSI palette inverts three rules, now enforced by `LightThemeContrastTest`: every `bright*` slot must be strictly **darker** than its base (bold text is ANSI 8–15 — brighten those on paper and every bold line fades out), ANSI 7 must not be near-white (1.27:1 on paper, and the render guard cannot rescue it because there the palette *is* the source), and the cursor is an opaque block so it is measured against the floor. ANSI 8 is the one structural exemption: it is the dim companion of ANSI 0, which on paper is the ink
- That floor forces BOSS Daylight's cursor to the darkened amber `#95580A` rather than the identity's `#D9871A`. The amber signal is 2.6:1 on paper — a block cursor at 2.6:1 is a smear — so the cursor and ANSI 3 take the darker amber (5.3:1) while the chrome still fills with the signature. A stated trade, not an oversight
- Fill tokens used as glyph colours are corrected: `ok` is 3.2:1 on both light identities and `warn` 3.3:1. The git branch label and sign-in toast take text tokens (the ⎇ glyph and the toast frame already carry the meaning) and the update banner's primary action takes `signalText`; its Info icon keeps `warn`, held to the 3:1 component floor
- Where the dark chrome distinguished two surfaces by *value* — a `#3C3C3C` field on a `#252526` panel — the token swap alone is not enough, because on the light identities `panel` and `raised` are one near-white step apart. Those places gain a `line` border so the shape survives in both directions
- Two sets of literals are kept deliberately, each with its reason recorded in place and allowlisted in the guard: the macOS traffic lights (macOS paints the same red/yellow/green in both appearances, and theming them would make BossTerm the only app on the machine whose close button is not red), and the scrollbar thumb/track, search markers and split focus border — those only look like chrome, they are `TerminalSettings` values the user owns, and pointing them at a token would let the active theme silently override a colour set in Settings
- `UiThemeTest`'s ladder test had the dark direction baked in, requiring light themes to step darker than their floor — it was asserting a property of `fromTheme`'s `mix(bg, fg, t)` derivation, not of a good surface ladder. Relaxed to strict monotonicity in whichever direction the theme declares: a collapsed rung is the bug, direction is the author's call
- **Guards.** `ChromeTokenCoverageTest` scans the 13 converted files for literals outside the allowlist, asserts each still reads a token (so the scan cannot pass vacuously on a file whose styling was deleted), and asserts the allowlist has no stale entries. Its pattern is widened and pinned by its own table test over 8 hardcoded and 8 prose/token shapes — it previously matched only `Color.White`/`Color.Black`, letting `Color.Red`, `Color.Gray` and `Color.Cyan` through, could not see the component constructor, and skipped comments start-of-line only, so a KDoc quoting a literal would have failed the build pointing at prose
- `LightThemeContrastTest` holds every slot to `TerminalSettings().lightBackgroundMinContrast` read from the setting rather than restated, so the palettes track the guard if its default moves, and asserts the guard is literally a no-op on all sixteen slots and the foreground — the real property, stated as identity rather than as a number. It also asserts solarized-light is the only light builtin below the floors, so the exemption cannot grow or go stale
- `ThemeDefaultsTest` gains the two palette pairs plus a sweep that every BOSS theme *has* a palette; four new `UiThemeTest` cases cover exact tokens, the host mirror, and that all four BOSS identities are actually reached by `EXACT_TOKENS` — a mistyped key would otherwise fall through to derivation silently. Each new assertion was verified by mutation: reverting a value fails exactly the intended test
- Known gaps, named in the coverage test rather than left implicit: `debug/DebugPanelComponents.kt` (27 literals) and `PreConnectScreen.kt` (20) are not converted — a dev-only panel and the SSH pre-connect screen
- The `AlwaysVisibleScrollbar` hoist comment gave a wrong reason: Compose does observe snapshot reads in the draw phase, so reading the token inside `Canvas` would still repaint. The hoist is right for cost, not correctness
