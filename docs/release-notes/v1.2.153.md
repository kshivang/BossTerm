# Release Notes - v1.2.153

**Release Date:** 2026-08-24

## Highlights
The focused pane's border was the last hardcoded colour on the pane surface — a generic blue belonging to no BOSS identity. It now follows the active theme, with a contrast floor so it stays visible on the light themes and a one-time migration so existing settings files actually pick the change up.

## Bug Fixes
- **The split focus border ignored the theme.** `splitFocusBorderColor` sat at the literal `0xFF4A90E2` while everything around it had been converted to tokens — the unfocused border is `UiTheme.line2`, the divider is `line`, the tab chips take the theme's cursor. It went unnoticed for as long as Blueprint was the default, because a generic blue on a blue identity looks intentional; on NVIDIA (green on pure black) the focus rectangle was the only non-green thing on screen. Ownership moves up a level to `splitFocusBorderColorOverride`, which is null until the user picks something, and only then does a colour beat the theme
- **A default change alone would have fixed nobody already running BossTerm.** An existing settings file has `0xFF4A90E2` serialized into it verbatim, so it would have stayed blue forever. `migrateSplitFocusBorderDefault` clears the old blue once on load, keyed on a `splitFocusBorderVersion` marker exactly as `migrateCursorRenderingDefaults` is. After that it is a colour like any other — the earlier approach of reading that value as "unset" inside `TerminalSettings` made it the one colour the picker could never select, a permanent hole rather than a one-time cost. The single case the migration gets wrong is a user who deliberately chose that exact blue; every other custom colour survives
- **The theme's signal was not guaranteed visible on its own floor.** Measured across all fourteen builtins, boss-daylight is 2.63:1 and solarized-light 2.98:1 — both under WCAG 1.4.11's 3:1 for a UI component, a regression the token switch would have introduced rather than one it inherited. New `UiTheme.focusRing` takes `signal` where signal clears the floor and `signalText` where it does not (5.32:1 and 5.34:1 on those two); the other twelve are unaffected
- **Match Theme lost the user's colour on a round trip.** Turning it off now restores the last explicit choice, held for the life of the settings window, rather than always writing the theme's own value
- Full transparency is no longer treated as an override — a 6-digit hex parses to alpha 0, which read as a deliberate choice while painting nothing

## Improvements
- Settings gains a **Match Theme** toggle in the Splits section. Turning it off writes the colour currently on screen, so the picker opens on what the user was looking at
- `SplitFocusBorderTest` holds every builtin theme to the 3:1 contrast floor through the `focusRing` property, so no by-name exemption is needed, and covers the migration. Both guards were verified by disabling them: dropping the contrast fallback fails the floor test, and dropping the clear-on-migrate fails the two migration tests
- Three existing assertions were weaker than they read. The "invisible on its own floor" check compared colours for exact inequality — which passes at 1.05:1 — and is now a real contrast check; the Blueprint assertion pinned a map lookup rather than a colour; and `ChromeTokenCoverageTest` no longer allowlists the literal on the grounds that it is "a colour the user owns", which was never true of the default
- The wiki's API reference and configuration tables document the new blank default
